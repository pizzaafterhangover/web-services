## 세부 구조도

<RosGraph
  client:visible
  nodes={nodes}

  width={880}
  height={700}
/>

- mission_fsm(Decision)이 `/planning/execute_task` 액션으로 작업을 맡기고, 대표 노드 planning_master(Planning)가 하위 플래너에 서비스·액션을 요청한다.
- 하위 플래너는 결과 토픽을 제어로 직접 보낸다. planning_master는 `/planning/drive_mode`만 직접 보낸다.
- 신호등은 traffic_behavior가 `/perception/traffic_light`를 직접 구독한다.

## 노드 목록

대표 노드는 ★로 표시했다. 전체 페이지의 노드 목록에서 이 파트만 옮겼다.

| 노드 | 하는 일 | 구분 |
| --- | --- | --- |
| mission_fsm | 미션 상태 머신 (Decision) | 직접 작성 |
| ★ planning_master | action 서버, 작업 분해. 하위 플래너에 서비스·액션 요청, `/planning/drive_mode` 발행 | 직접 작성 |
| planner_server | Nav2 SmacPlanner2D, global_costmap. 전역 경로 | 기존 패키지 |
| approach_planner | 선반 앞 정렬 pose | 직접 작성 |
| grasp_planner | 서 있음: 위 / 누움: 측면 + 롤 | 직접 작성 |
| arm_ik_planner | 5축 해석적 IK, 간섭 검사 | 직접 작성 |
| bin_manager | 적재통 슬롯(가로 배치, 위치 **[미정]**) | 직접 작성 |
| traffic_behavior | 신호등 RED/YELLOW → HOLD | 직접 작성 |
| health_monitor **[보류]** | 이전 설계의 장애 판정 노드. 새 차트에 없어 유지 여부 미정 |  |

  새로 정하기 전까지 이 페이지에는 옛 정의를 싣지 않는다. 위 표의 **[타입 미정]** 토픽·서비스·액션이 새 메시지 후보다.
</Callout>

## 통신 규칙

- **하위 플래너가 결과 토픽을 제어로 직접 발행**한다. planning_master는 서비스·액션 요청과 `/planning/drive_mode`를 맡는다.
- **신호등은 traffic_behavior가 `/perception/traffic_light`를 직접 구독**한다.
- 받는 쪽은 보내는 쪽 QoS에 맞춰야 한다. 맞지 않으면 에러 없이 메시지가 안 온다. 토픽별 QoS 표는 새 토픽 기준으로 **[개정 필요]**.
- 받는 쪽은 `header.stamp`를 보고, 예를 들어 0.5초 넘게 새 메시지가 없으면 멈추는 처리를 넣는다.
- 콜백에서는 값만 저장하고, 판단은 타이머에서 최신 값을 보고 내린다.
- 측면·후방 사각 때문에 costmap inflation을 0.33 m 이상(외접원 283 mm + 여유 50 mm)으로 둔다 **[검토 중]**.

### yaw 범위 규칙 [검토 중]

이전 설계의 규칙이다. grasp_planner(서 있음: 위 / 누움: 측면 + 롤) 기준으로 다시 확인한다.

| 퍽 상태 | 대칭 | 보낼 범위 |
| --- | --- | --- |
| 서 있는 원통 | 어느 방향이든 같음 | 0 고정 |
| 서 있는 직육면체 | 90°마다 | −45°에서 +45° |
| 누운 원통 · 직육면체 | 180°마다 | −90°에서 +90° |

공통 설정: 모든 노드는 같은 `ROS_DOMAIN_ID`와 같은 RMW 구현을 쓴다. 카메라 노드는 한 곳에서만 실행하고, 컨테이너를 나눌 때는 `--network host --ipc host`를 쓴다.
